# План: инструмент `run_skill` (C2)

## Проблема

Сейчас агент в mini-ai-1c использует скиллы так:
1. `search_skills` / `list_skills` → найти скилл;
2. `get_skill` → прочитать SKILL.md, распарсить команду `powershell.exe -NoProfile -File 1c-epf-build/scripts/epf-build.ps1 ...`;
3. Вручную сконструировать путь к скрипту относительно каталога скиллов;
4. Выполнить через `run_command` (mcp-1c-filesystem) с `cwd` = каталог скилла.

Проблема: шаги 2-4 хрупкие — агент может неверно собрать путь (был конфликт с `skills/` префиксом), неправильно задать `cwd`, забыть про `.py`-версию на Linux. Выполнение одного скилла требует 3-4 tool calls и может упасть на путях.

## Цель

Инструмент `run_skill` (или Tauri-команда), который берёт на себя шаги 2-4:
- агент вызывает `run_skill(id, args)` — сервер сам находит скрипт, определяет рантайм (PS1/Python), строит команду и выполняет её;
- один tool call вместо 3-4.

## Архитектура

### Вариант A: расширение mcp-1c-skills (рекомендуется)

В `tauri-app/mcp-1c-skills` добавить tool `run_skill`:

```
run_skill {
  "id": "1c-skills/1c-epf-build",      // ID скилла (как в get_skill)
  "args": { "-SourceFile": "src/Моя.xml", "-OutputFile": "build/Моя.epf" },
  "cwd": "src/cf",                     // рабочая папка (опционально, по умолчанию — каталог скилла)
  "timeout_ms": 60000
}
```

Логика:
1. `skill_dir_from_id(id)` → каталог скилла;
2. Прочитать `SKILL.md`, распарсить блок `## Команда` (или лучше — взять `scripts/` и имя из frontmatter/файловой системы);
3. Выбрать рантайм: на Windows `.ps1` (через `powershell.exe -NoProfile -File`), на Linux/macOS `.py` (через `python3`);
4. Собрать команду: `powershell.exe -NoProfile -File <abs>/scripts/<script>.ps1 <args>`;
5. Выполнить в `cwd` (по умолчанию каталог скилла), вернуть stdout/stderr/exit_code.

**Плюсы:** сервер уже знает структуру скиллов, пути резолвятся внутри. Минимум новых зависимостей (std::process::Command — уже используется в mcp-1c-filesystem).
**Минусы:** mcp-1c-skills сейчас read-only (только сканирование); добавление исполнения меняет его роль — нужно обдумать sandbox.

### Вариант B: Tauri-команда `run_skill` в src-tauri

Добавить в `commands/skills.rs` Tauri-команду, которая:
- резолвит каталог скилла через `resolve_skills_dir()`;
- парсит SKILL.md → находит скрипт;
- запускает через `std::process::Command` (уже используется для EditorBridge/др.).

**Плюсы:** без изменений MCP-сервера; проще добавить ограничения (только scripts/, whitelist путей).
**Минусы:** дублирует логику резолва путей; агент (через MCP) не сможет вызвать напрямую — понадобится проброс в naparnik_client как tool.

## Ключевые решения

1. **Откуда брать команду — из `## Команда` в SKILL.md или из файловой системы?**
   - Из SKILL.md: рискованно — формат различается, парсинг хрупкий.
   - Из файловой системы (найти `scripts/*.ps1`/`*.py`): надёжнее. Рекомендую: брать имя скрипта из блока `## Команда` (первые упоминание `-File ...`) как источник истины, а существование проверять по FS. Fallback — единственный скрипт в `scripts/`.
2. **Рантайм:** PS1 = мастер, Python = порт. Выбор: Windows → `.ps1`, иначе → `.py` (совпадает с `python-porting-guide.md`).
3. **Безопасность:** запретить выход за каталог скилла для скрипта (только `scripts/*`); `cwd` — произвольный (рабочая папка проекта), как у `run_command`.
4. **Аргументы:** передавать как flat-список `-Key value`; пользователь/агент передаёт уже готовые флаги. Сервер не валидирует параметры (это делает сам скрипт).
5. **Возврат:** `{ stdout, stderr, exit_code, duration_ms }` — тот же контракт, что у `run_command` (mcp-1c-filesystem).

## Реализация (шаги)

1. **`tools.rs` (mcp-1c-skills):** добавить `run_skill` в `list_tools()` + обработчик в `call_tool`:
   - резолв `skill_dir_from_id`;
   - выбор скрипта (`scripts/<script>.ps1` или `.py`) с приоритетом по ОС;
   - сборка командной строки;
   - `std::process::Command` в `cwd`;
   - таймаут (по умолчанию 60s, clamp 1s..300s) — по аналогии с `tool_run_command`.
2. **`skills.rs`:** возможно, добавить хелпер `resolve_skill_script(skill_dir) -> Option<PathBuf>`.
3. **Тесты:** 
   - `run_skill_basic` — временный скилл с `scripts/hello.ps1`/`hello.py`, проверить stdout/exit_code;
   - `run_skill_no_scripts` — скилл без скриптов → ошибка;
   - `run_skill_linux_prefers_py` — на не-Windows выбирается `.py`.
4. **`list_tools()` описание** — для агента: «Выполнить скрипт скилла. Передаёт аргументы скрипту, возвращает stdout/stderr».

## Объём

- `mcp-1c-skills/src/tools.rs`: +~60 строк;
- `mcp-1c-skills/src/skills.rs`: +~20 строк (хелпер выбора скрипта);
- `mcp-1c-skills/src/tools.rs` (тесты): +~30 строк;
- итого ~110 строк, 1 файл тестов.

## Риски

- **Пути:** агент передаёт `cwd` относительно sandbox mcp-1c-filesystem, а не mcp-1c-skills. Уточнить: `run_skill` выполняется в ОС-процессе сервера — `cwd` должен быть абсолютным или относительно рабочей папки сервера. Возможно, `cwd` лучше не принимать, а выполнять в каталоге скилла (скрипты работают с относительными `src/`, `build/` от CWD проекта). **Требует обсуждения.**
- **Параметры с кавычками:** `-Synonym "Загрузка прайс-листа"` — нужно передавать как отдельные аргументы (Vec<String>), не строкой.
- **Не-1С скиллы** (desktop-framework-tauri и т.п.) могут не иметь scripts/ — `run_skill` должен мягко падать с понятной ошибкой.

## Решение по `cwd` (рекомендация)

Не принимать `cwd` в первом релизе. Выполнять скрипт в **каталоге скилла** — это устраняет проблему «несоответствия путей относительно скрипта» (текущий баг с `skills/` префиксом). Скрипты, которым нужна рабочая папка проекта, получат её через параметр `-SrcDir`/`-OutputFile` (абсолютные или относительно каталога скилла).

Если выяснится, что скриптам нужен CWD проекта — добавить `cwd` параметр с валидацией (абсолютный путь, как у run_command).
